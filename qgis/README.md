# Local PET scenario updates

`POST /pet/update?session_id=<uuid>` recalculates the changed objects' cells and
their eight neighbours on the **existing wind grid**. It preserves the session's
PET pixels outside those cells. The backend exposes this as `POST /update-pet`;
the frontend sends its existing stable object IDs with the complete object list.
Select **PET (Updated)** in the map layers to see the result after saving.

## How it works

1. `scenario_grid.py` reads `/data/server/wind-speed-calc.geojson`, validates its
   EPSG:28992 rectangles and indexes them by `(col_index, row_index)`. The supplied
   Middelburg grid has 140 m by 280 m cells. Shared edges belong to the east/south
   cell. Neighbours outside the grid or calculation coverage are omitted.
2. `local_pet_service.py` compares the submitted objects with the last accepted
   snapshot. It selects both locations for moves, old locations for removals, and
   deduplicates overlapping neighbourhoods. A save without changes does no raster
   work. Reordering overlapping objects also triggers calculation: later objects
   still overwrite earlier ones, matching the existing burning behaviour.
3. Adjacent selected cells are combined into rectangles without including gaps
   between distant edits. Each rectangle reads an extra 16 m of context for
   hillshade, resampling and the existing 10-pixel NoData search. Only the selected
   core is written back. Input crops retain their native resolution (0.5 m DSM,
   1 m prepared PET inputs in the supplied data).
4. The existing Bowen/sun-PET/hillshade/final-PET/NoData-fill stages run on each
   crop. Local calculation uses exact aligned pixel windows; it avoids the legacy
   custom-extent path's extra east/south row and column. The final session raster
   retains the original dimensions and border pixels outside input coverage.
5. A new copy of the previous session PET receives the patches. Each request has
   a private temporary workspace. A per-session file lock serializes saves.
   `map.qgz` embeds `pet-scenario.json` alongside the QGIS XML: the object snapshot
   and published raster pointer are replaced together atomically. A failure keeps
   the previous map and objects. The response's `output` is the published filled
   raster; `updated_cells` and `timings_seconds` explain the work performed.

Tree foliage still uses the existing random radial distribution and jitter, but
the local path gives each object a stable SHA-256-derived seed from its ID.
This makes unchanged trees repeatable across overlapping updates and restarts.
Legacy clients without IDs receive deterministic content-based IDs. Changing an
anonymous object's properties is treated as removing it and adding another.
Full base-map generation keeps its existing behaviour.

## Inputs and boundaries

Required prepared inputs are `dsm.TIF`, `raster/br-reproject.tif`,
`raster/svf-reproject-filled.tif`, `uhi/sun-bbox.tif`, `uhi/shadow-pet.tif`, and
`server/wind-speed-calc.geojson`. The baseline PET is read from the session
project's `pet-version-1` layer. Inputs must share compatible north-up EPSG:28992
pixel alignment; the prepared PET inputs must use the current 1 m resolution.
The grid and rasters are external datasets, not generated by this feature.

A new session starts from the baseline and treats all submitted objects as new.
A legacy session without an embedded snapshot likewise rebuilds its submitted
scenario from the baseline, because previous removed objects cannot be recovered
from the old raster. Subsequent updates preserve edits outside selected cells.
Input size/mtime and algorithm version are recorded; a changed input requires a
new session to avoid mixing calculation versions. Size/mtime is a quick change
check, not a cryptographic provenance guarantee.

Object centres outside common raster coverage are rejected. An object whose
radius plus jitter/context reaches a whole cell width/height is rejected rather
than silently extending the agreed 3 x 3 selection. Small placements are the
supported workflow. The input list is a complete snapshot: an empty list removes
all previously saved objects. Concurrent saves are serialized; the last complete
snapshot wins, as with the existing interface.

The feature reuses prepared wind, sky-view-factor and shadow-PET inputs. It does
**not** integrate wind regeneration, change weather/date assumptions, or provide
a new physical tree/shadow model. All measure types still follow the existing
point-processing equations. Matching the current full calculation is regression
evidence, not scientific validation of PET. The supplied baseline should represent
the same prepared inputs: unrelated baseline differences can otherwise become
visible when a region is recalculated.

## Verification

Run the offline GIS suite in the existing QGIS environment:

```sh
docker compose exec -T qgis python3 -m pytest tests/test_local_pet.py -q
```

It covers index selection, boundary ownership, overlapping/distant edits, moves,
deletion, repeatability, NoData, exact full-versus-local values, unchanged outside
pixels, state after restart, failed calculation/publication, and session locking.
It needs no external services or production datasets. The separate wind tests
require real DSM/DTM files and network access; they are not PET regression tests.

For an opt-in comparison using the supplied Middelburg inputs:

```sh
docker compose exec -T qgis python3 tools/validate_local_pet.py \
  --output /tmp/local-pet-check --revision <revision-and-local-changes>
```

Use a new output directory for each run. The script generates private full and
local outputs, compares every pixel in the selection, checks outside preservation
and deletion, and hashes source files before and after. `report.json` records
input hashes, software versions, scenario, stage timings and limitations. It uses
the previously reviewed one-tree position `(31740, 391420)` with height 15 m and
radius 5 m. Full-reference foliage uses the same object seed for a valid comparison.
The legacy full-reference extent/alignment settings are retained independently
of the new cropped path.

Timings are sequential service-level observations with uncontrolled cache state;
full reference excludes project publication, local includes it. Record host and
Docker limits separately, repeat representative scenarios, and agree performance
and scientific targets before claiming acceptance. Calculation still copies a
whole final GeoTIFF per successful save and retains previous revisions. More
advanced storage and cleanup policies are separate work.

The API uses GDAL window reads/writes documented in the
[raster API](https://gdal.org/en/stable/api/python/raster_api.html) and the existing
[NoData filling](https://gdal.org/en/stable/programs/gdal_fillnodata.html) settings.
The implementation was exercised in QGIS 4.3.0-Master / GDAL 3.10.3; verify other
deployment versions with the offline suite before use.

### Observed local verification (September 2026)

On an Apple M2 laptop with 16 GiB RAM, Docker's VM had 8 CPUs and about 7.65 GiB
RAM; the QGIS image ran as x86_64 without a separate container resource cap.
The single-tree exploratory check took 27.95 s for the legacy full reference
and 3.81 s for the local service, with 352,800 pixels in nine selected cells.
Every selected pixel and validity mask matched exactly, and no outside pixel
changed. Deletion also matched the full no-object calculation exactly.

A separate request through Vite, backend and QGIS took 4.89 s, followed by a
successful WMS PNG render. Its addition/removal outputs were subsequently
compared with the full references with the same exact agreement. All supplied
input hashes remained unchanged. These are exploratory observations with the
timing boundaries above, not a guaranteed speedup across scenarios or hardware.

The supplied displayed baseline differs from a no-object full recalculation at
33 pixels (same validity mask). This predates local patching: deletion reproduces
the no-object calculation in the selected cells, which need not be byte-identical
to the supplied historical baseline. Its provenance needs separate confirmation.

A later isolated comparison on 30 September 2026 used three initial saves per
version and scenario with the same request boundaries and input sets. Median
backend request times were 37.58 → 4.27 s for one tree and 28.70 → 19.47 s for ten
distributed trees. Comparison scenarios are in `benchmark/scenarios/`; generated
evidence remains local under `benchmark/runs/` and `benchmark/comparisons/`.
These observations measure scenario updates, not base-map generation.

Those fresh runs also showed 1,715,025 / 1,602,537 differing NoData pixels between
full and local outputs for one / ten trees. A blockwise check located all mask
differences outside the selected cells; masks agreed inside, and the local path
preserved the supplied baseline outside. The earlier controlled-reference result
must therefore not be generalised to these runs. Baseline provenance and the
different reference conditions remain unresolved. Uncontrolled legacy foliage
also prevents treating finite before/after differences as scientific validation.
